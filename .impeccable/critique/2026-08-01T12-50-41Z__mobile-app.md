# Vigorly product and interface critique

> This document preserves the point-in-time baseline findings. The implementation pass completed later the same day resolved activation, repeat logging, Health provenance, fabricated fallback values, reduced motion, shared touch targets, visual hierarchy, and the broken web export. The remaining P1 work is broader mobile store/routing test coverage and eliminating catalog drift between runtimes.

## Executive assessment

Calorie Lens is an unusually credible fitness product underneath a polished but over-repeated visual system. Its strongest product idea is not the dark lime styling; it is the accuracy contract: deterministic local parsing, explicit ranges, source labels, assumptions, clarification before save, encrypted local storage, and a complete offline mode. The highest-impact work is activation and daily-loop compression, followed by accessibility/motion hardening and removal of parallel calculation paths.

## What is working

- The capture -> clarify -> review -> confirm loop makes uncertain estimates inspectable before they enter the ledger.
- Food logging is differentiated by visible midpoint, range, confidence, basis, and source.
- The native product is local-first, encrypted, interruption-safe, and does not require an account.
- Five labeled tabs are understandable and the visual language is consistent across store screenshots.
- Training depth, Health integration, backup/restore, and on-device coaching make the product substantially more complete than a calorie counter.
- Typecheck, lint, Python compilation, and all 23 Python unit tests passed.

## Detailed findings

### P1 — Activation asks for commitment before demonstrating value

The first run is ten screens and most are blocking. The router then sends the user to a second auth/offline decision before the first useful log. Collect only the minimum needed for a starter target, let the user log a meal, and progressively request training, diet, coaching tone, bowl calibration, Health, and account setup later.

Evidence: `mobile/app/onboarding.tsx:55`, `mobile/app/onboarding.tsx:215`, `mobile/app/onboarding.tsx:283`, `mobile/app/_layout.tsx:110`.

### P1 — The public web companion contradicts the trust promise for unknown foods

The current Streamlit fallback silently assigns generic calories and macros to unmatched foods. The native product correctly asks a clarification instead. A single unknown-food behavior should exist everywhere; guessing undercuts the most defensible product advantage.

Evidence: `app.py:603`, especially the unmatched branch at `app.py:624`.

### P1 — Mobile high-risk behavior has no automated test layer

The mobile package has lint and typecheck scripts but no unit or end-to-end tests. The untested surface includes local/cloud merge, encrypted hydration/reset, meal parsing, workout calculations, active-session persistence, and onboarding/auth routing. Add golden cross-runtime fixtures first, then store/parser tests and a small device E2E smoke suite.

Evidence: `mobile/package.json:5`, `mobile/src/store/app-store.tsx:194`, `mobile/src/store/app-store.tsx:318`.

### P1 — The declared web target does not currently bundle

Both Expo dev-server attempts failed to expose a listener, and static export failed because Expo SQLite's `wa-sqlite.wasm` could not be resolved. If web is supported, fix or explicitly isolate the storage adapter. If the native app is the only product, remove the misleading web script/dependencies and document that boundary.

Evidence: `mobile/package.json:9`, `mobile/src/lib/secure-storage.ts:5`.

### P1 — Motion has no reduced-motion path and is over-applied

Shared `Reveal`, `Bar`, `Segmented`, tab, and count-up primitives animate by default, with many simultaneous instances. There is no `AccessibilityInfo` or equivalent reduced-motion check. CountUp also schedules React state updates on every animation frame. Reserve motion for state changes and achievements, disable decorative entrance staggering under reduced motion, and avoid animating every number on every mount.

Evidence: `mobile/src/components/ui.tsx:151`, `mobile/src/components/ui.tsx:242`, `mobile/src/components/ui.tsx:430`, `mobile/app/(tabs)/_layout.tsx:84`.

### P1 — Several controls are smaller than the stated 44-point accessibility target

Chips are 34 points high, the segmented control is 40, pills are 24, and some Train/Quick Log controls are 34–38. Some call sites compensate with hit slop, but the shared primitives do not consistently guarantee a 44-point interactive area. Add minimum hit areas in the primitives and test Dynamic Type / screen-reader state.

Evidence: `mobile/src/components/ui.tsx:847`, `mobile/src/components/ui.tsx:859`, `mobile/src/components/ui.tsx:947`, `mobile/app/(tabs)/train.tsx:678`.

### P1 — A coherent design system has become a repetitive screen template

Near-black canvas, ambient glow, raised 24-radius hero, uppercase eyebrow, count-up number, three metrics, and reveal staggering recur across most screens. The screenshots are polished and consistent, but the same hierarchy makes Today, Food, Train, Progress, and Coach feel more alike than their jobs are. Keep the palette and typography; give each primary task its own compositional grammar and reduce shadows/glows to true focal moments.

Evidence: `mobile/src/theme.ts:140`, `mobile/src/theme.ts:142`, `mobile/src/components/ui.tsx:54`, `mobile/src/components/ui.tsx:95`, `mobile/src/components/ui.tsx:300`.

### P1 — Health data lacks an explicit freshness and reconciliation contract

StepsApp reviews repeatedly show that users interpret delayed or merged data as broken counting. Calorie Lens stores `lastHealthSync`, but the core model mainly replaces daily values and exposes limited source/freshness context. Every imported metric should show source, last refresh, expected latency, and whether a manual value was replaced; provide retry and undo where practical.

Evidence: `mobile/src/store/app-store.tsx:255`, `mobile/src/store/app-store.tsx:567`.

### P1 — Domain logic can drift across three implementations

The reviewed Python calorie engine, the mobile TypeScript catalog/parser, and the 2,477-line Streamlit app carry parallel food and command logic. The mobile catalog explicitly says it mirrors Python manually. Generate both catalogs from one source and run shared golden fixtures in both runtimes; then split the Streamlit monolith or make it call the canonical engine.

Evidence: `mobile/src/lib/food-catalog.ts:9`, `api.py:25`, `app.py:166`, `app.py:603`.

### P2 — The daily logging loop needs a zero-thinking repeat path

Voice and typed natural-language logging are thoughtful, but repeat meals currently go through capture and review again. Add recents, favorites, saved meals, and one-tap “repeat yesterday's breakfast,” while retaining review when the estimate is new or uncertain.

Evidence: `mobile/app/quick-log.tsx:74`, `mobile/app/quick-log.tsx:95`, `mobile/app/quick-log.tsx:474`.

### P2 — Train is powerful but presents too much at one hierarchy level

The tab combines weekly hero, routines, templates, muscle distribution, history, and settings. Make “resume/start workout” the dominant action; move templates and configuration one level deeper, and reveal analysis after the user has completed sessions.

Evidence: `mobile/app/(tabs)/train.tsx`.

### P2 — The product needs glance surfaces, not more primary tabs

Borrow StepsApp's widget and watch lesson: show calories remaining, protein, steps, and an active rest timer on lock-screen/home/watch surfaces. This increases daily value without adding navigation complexity.

## Independent assessment comparison

- Assessment A (manual/source/screenshot review) found strong hierarchy and trust patterns but substantial onboarding friction, motion/accessibility gaps, visual sameness, and daily-loop inefficiency.
- Assessment B's deterministic detector scanned 24 TSX files and returned zero rule matches. That clean result is useful but narrow; runtime inspection was unavailable. Its static Expo export exposed the unresolved SQLite WASM failure.
- The two assessments agree that the source is systematically tokenized and avoids obvious markup anti-patterns; the important shortcomings are product-flow, runtime, accessibility, and system-level repetition rather than isolated invalid JSX.

## Recommended sequence

1. Compress onboarding and remove the second activation gate.
2. Add recent/favorite/repeat logging and a single next-action Today surface.
3. Establish shared accuracy fixtures and mobile test coverage; eliminate the Streamlit guessing path.
4. Add Health freshness/source/reconciliation states.
5. Implement reduced motion and 44-point hit targets; then simplify repeated glow/card composition.
6. Add widgets/watch surfaces only after the core loop is reliable.
